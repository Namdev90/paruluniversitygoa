# Disabled notification and release-hint Worker proposal

The checked-in package is an offline candidate. It has not been deployed or configured with live credentials. Target is the existing Cloudflare account 086fa0481ec044a8a2d474f83e22f88e; Workers Free only, without a paid upgrade or card.

Proposed Worker `navrang-notifications` exports singleton SQLite Durable Object `NavrangNotificationOwner`, binding `NOTIFICATION_OWNER`, migration `v1`. Compatibility date 2026-10-26, `nodejs_compat`, workers.dev and previews false, observability false. No cron, public route, database binding, Firebase project, issuer secret or certificate is in checked-in configuration. `NOTIFICATION_ENABLED`, `NOTIFICATION_QUALIFIED`, `RELEASE_HINT_ENABLED`, `RELEASE_HINT_QUALIFIED`, `RELEASE_SIGNER_VERIFIED` and `AUTH_DB_CACHE_DISABLED` all default false. Creating this Worker or its namespace requires the specific future approval for that resource; approval for the two existing disabled voice Workers did not include this one.

The scheduled path calls the existing private leased outbox and rechecks authorization before sending. The SQLite owner persists a UTC daily limit of 10,000 notification database operations, 1,000 OAuth exchanges and 1,000 FCM sends; it fails closed on exhaustion and clock rollback. Release actor checks have a separate 100/day cap, and published-manifest reads a 1,000/day cap. These counters do not cover all account traffic, Worker/DO CPU, storage or ingress quotas, and other applications may consume shared limits. They are not evidence of available Free entitlement or a guarantee of a particular duration; the Free plan and real usage must be verified before activation. Provider acceptance is not device receipt, and ambiguous outbox delivery can require client reconciliation.

The separate `/release-hint` endpoint remains unavailable while disabled and without an approved route. It accepts only version code and digest, authenticates the raw existing bearer by hashing it and resolving an active admin via the existing private SQL function, then independently fetches the fixed public updater manifest without redirects or cache. It verifies the updater's canonical `navrang-release-v1` signature against a public X.509 certificate whose SHA-256 must equal the existing original signing certificate pin in tools/release_policy.py. A SQLite ledger claims each version and exact digest before send; an uncertain result is never automatically retried. A provider request already admitted cannot be recalled after cancellation. The currently retained 0.8.0 metadata lacks the required original-key signature and fails closed.

Before activation identify the existing Supabase connection identity/custodian and authorize an uncached Hyperdrive binding named `NOTIFICATION_DB`, with actual cache-off setting verified independently; `AUTH_DB_CACHE_DISABLED=true` alone is not proof. Identify an existing narrowly scoped FCM project/service account/key, approve importing that existing RSA key only as `FCM_SERVICE_ACCOUNT_KEY` and configuring email, key ID and project ID. No key generation, IAM change or project creation is implied. Identify the original public signer certificate DER and verify its pinned fingerprint; the private Android signing key stays with its custodian and is never uploaded. `RELEASE_SIGNER_VERIFIED=true` and the qualification flags may only be set after evidence and scoped approval, not as evidence themselves.

Separately approve an exact schedule and, if release hints are desired, the exact authenticated endpoint route and upstream caller. Run synthetic authorization, outage, timeout, quota, eviction, duplicate and disabled-flag qualification before enabling delivery; then validate original-app/original-signer device permissions, background behavior, rotation, logout/unlink, stale ordering and privacy. No live provider sends, credentials, security configuration, billing changes, signing or phone access were performed by this offline work.
