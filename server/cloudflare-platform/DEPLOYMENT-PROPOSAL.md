## Persistence, cleanup and limits

Controller owner persists last successful authenticated activity and a daily SQL-operation counter in SQLite. In-memory sockets/keys are reconstructed after eviction; the existing exact `inspect-room` receipt protocol recovers only the same stable controller identity/version, room, publisher and deadline. No missing room or uncertain socket closure is accepted as revocation proof. SQL is still the authoritative durable cleanup queue; relay SQLite remains exact grant/retirement authority.

An alarm is saved before request execution so interrupted authorized work can be cleaned up. Successful authenticated responses extend a maximum five-minute cleanup window; failed/fake sessions cannot extend that window. Cleanup alarms run at one second while the window is active, then sockets/pool close. Failures retry every30seconds only within that window. An expired window leaves SQL work durable; the next request performs cleanup before admission. Alarms are not timing/security proof: media relay enforces deadlines on every frame independently.

The package permits at most80,000 private SQL queries per UTCday, persisted in singletonSQLite, then fails closed until nextday. This reserves nominal headroom below Hyperdrive Free100,000 dailyqueries; other applications on the account may consume shared quota, so it cannot guarantee availability. There is no paid fallback. Free Worker/DO CPU, request, duration and storage limits can stop service earlier. High-rate voice is not guaranteed to fit a day's free quotas; qualify measured workloads before activation. Neither configuration flags nor a successful dry-run prove live cutoff/clock behavior.
