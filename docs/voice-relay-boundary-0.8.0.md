# Voice relay boundary: 0.8.0

Checked 25 October 2026. This source adapter is staged work, not an operational voice service. No provider credentials, live media or production requests were used to verify it.

`server/voice/livekit-relay.mjs` signs receive-only room credentials with an explicit TTL of 1–600 seconds (60 seconds by default), and authenticates bounded Cloud `RemoveParticipant` requests. Room and participant names must be opaque server-owned identifiers, supplied after a fresh duty and authorization check. The adapter is not a public token endpoint; callers must also enforce the communications readiness gate. Tokens contain no publishing, data publishing, metadata modification or administrative grant.

Removal always includes `revoke_token_ts`; it does not substitute a permissions downgrade or rely on the provider's default cutoff. The cutoff covers the configured request deadline plus one second, since an equal `nbf` is not earlier than the cutoff and a token can refresh during removal. A response received after that local cutoff is not acknowledged. Clock synchronization, refreshed-token rejection, provider propagation and real connected-media removal still require isolated transport tests. Failed, ambiguous, timed-out and malformed responses remain unacknowledged. No retries occur inside the transport; durable controller state owns retries.

Publishing and lease renewal always return `ACTIVE_MEDIA_FAILSAFE_UNAVAILABLE`. Readiness reports the expiry and controller-death gates as false, regardless of configuration flags. A short token TTL does not stop already connected media. Starting a separate watchdog before sending a publish permission update is also insufficient: that update can reach the relay after the watchdog has already removed the participant. A fresh controller heartbeat cannot close this race.

Before enabling voice, the relay must own an atomic fenced grant/deadline protocol that rejects stale generations and late grants and independently terminates active media at expiry, including after controller death, stalled network requests and relay restarts. A provider-supported mechanism with equivalent properties would also qualify. The implementation requires two isolated identities to prove half-duplex contention, administrator preemption, revoked initial/refreshed/reconnect token rejection, expired media termination and duty/session cleanup. Local mocked transport tests are not that evidence.

Official references:

- [LiveKit tokens and grants](https://docs.livekit.io/frontends/reference/tokens-grants/) documents Cloud's ten-minute revocation retention and self-hosted cached-token limitations. Consequently this adapter only accepts direct secure `*.livekit.cloud` origins and caps minted TTLs at ten minutes; it does not label self-hosted short TTLs as safe revocation.
- [Room service API](https://docs.livekit.io/reference/other/roomservice-api/) specifies Twirp JSON POST requests, bearer authentication, room-scoped admin grants and the explicit cutoff's 60-second acceptance window. `UpdateParticipant` does not offer the explicit removal cutoff used here, so this adapter deliberately disconnects revoked identities.
- [LiveKit's token signer](https://github.com/livekit/node-sdks/blob/main/packages/livekit-server-sdk/src/AccessToken.ts) establishes the HS256 JWT claim format. [Room service client](https://github.com/livekit/node-sdks/blob/main/packages/livekit-server-sdk/src/RoomServiceClient.ts) confirms room-scoped removal authorization and the int64 cutoff. The implementation uses platform Web Crypto and the documented JSON protocol, adding no SDK dependency.
