# Approved biometric app-lock integration

The user approved enforcement for every authenticated user, cold-start locked, with a 30-second background grace period. AppLockState.java now implements the process-memory policy and passes 21 JVM boundary checks. Android biometric presentation, activity/route/bridge gates and physical-device acceptance are still unfinished; this policy class alone does not lock the installed app. Session renewal has its separate explicit approval and implementation.

The current native MainActivity.kt extends the generated ClassicActivity host, while app/java/in/navrang/gate/MainActivity.java owns the bundled WebView, auth bridge, scanner handoff and onResume/onPause hooks. A future local app-lock gate would need to hide private content and prevent protected bridge/scanner actions before showing them, rather than merely covering the screen after it renders. Internal camera, permission, file picker and installer transitions must be distinguished from a true app-background transition to avoid prompt loops and lost operations.

GateSession.java encrypts access, refresh and pending successor credentials with AndroidKeyStore AES/GCM under the existing navrang-session-v2 alias. That key does not require biometric authentication and has not been replaced. App-lock UI must use strong biometrics or supported device credential. The original APK signing key is a different key and must also be preserved.

Native MainActivity.onPause already cancels Talk intent through VoiceSessionClient; VoiceSessionService may retain an explicitly started authorized receive session. A biometric lock therefore needs a deliberate policy for audible receive while locked, microphone cancellation, expiry and safe unlock. It must not start background microphone access or silently revive a stopped voice session. Scanner results, pending admissions and file saves need identity/generation fencing through cancellation and unlock.

The approved boundaries are settled: genuine app background, elapsedRealtime clock, reuse only below 30,000 milliseconds; at 30,000 or later require authentication. A process restart always locks. Screen/device lock invalidates current unlock and prompt callbacks. Do not persist an unlocked flag, exempt voice/scanning, or prompt repeatedly on rotation or the prompt's own lifecycle. AppLockState is deliberately separate from Android presentation so lifecycle and prompt generation fences can be tested without pretending that a fake fingerprint establishes device acceptance.

Android's official [biometric guide](https://developer.android.com/identity/sign-in/biometric-auth) distinguishes Class 3 biometrics and device credentials. Strong-plus-device-credential combinations are unsupported on API29 and earlier; check KeyguardManager.isDeviceSecure there and provide a separate supported credential flow. [AndroidX release notes](https://developer.android.com/jetpack/androidx/releases/biometric) list 1.1.0 as stable on the inspection date. UI-lock authentication with PIN fallback does not imply automatic invalidation of the existing encryption key when biometric enrollment changes.
