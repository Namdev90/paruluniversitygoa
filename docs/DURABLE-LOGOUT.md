# Native logout revocation recovery (source change)

Native logout blocks private access and fences old profile, sign-in and renewal callbacks immediately. Before reporting local sign-out success, one synchronous preferences transaction moves the existing AndroidKeyStore AES-GCM credential envelope from the active session slot to a UUID-keyed revocation-only queue and removes the active slot. Moving ciphertext works even when the keystore cannot currently decrypt it. A failed commit is reported as an incomplete sign-out; the current process stays blocked and rejects new credential saves until the same captured operation is successfully retried.

Queue entries are not sessions: `read()` never returns them, renewal cannot use them, and they are not sent to the WebView, exports, notifications or logs. Multiple offline account switches retain separate encrypted entries. The existing installation identifier and keystore alias are unchanged. The queued envelope may include its old profile and pending rotation, but HTTP receives only its captured access/refresh credentials. No new credentials are generated by logout.

While the application is foregrounded (including a locked or signed-out screen), the existing runtime scheduler retries queued revocations independently of private reconciliation. There is no new background service or inactivity-extending renewal. Per-entry exponential retry intervals grow from 1 to 60 seconds; each pass attempts at most four entries in earliest-due order, with a stable ID tie-break so repeated slow failures cannot starve later accounts. Keystore, network and response failures retain the item. A response must explicitly contain HTTP 200, `ok: true` and `signedOut: true` before the exact queue item is removed durably. Failed removal commits retain the item in the coordinator even if Android preferences already changed in memory. Retrying a completed server revocation is idempotent.

The existing server session-revoke contract resolves even consumed refresh hashes to their original family, checks installation identity and revokes the family. It acknowledges an already absent family. Legacy logout uses only the captured legacy access token; the transport must never substitute the current account's token. Revocation responses do not alter the active session, permissions, local records or account UI.

## Evidence and limits

`python3 tests/native-logout-revocation-check.py` executes the real encrypted vault and retry coordinator with synthetic credentials, HTTP responses, a test keystore and disk failures. The existing vault, renewal and runtime tests also run in `npm run test:native`.

Successful local sign-out means the revocation intent is durable, **not** that the server was contacted while offline. Server revocation requires opening the app with connectivity and an available keystore. Clearing app storage/uninstalling, permanently losing the keystore, corrupted stored ciphertext, or a device never reconnecting can prevent delivery; server-side expiry still applies. No application can guarantee persistence when the storage write fails: an unconfirmed failed sign-out or process termination before its transaction completes must not be presented as durable logout. After a failed write, keep the app open and retry sign-out.

This is a source-only change. It does not modify production data, deploy backend changes, enable locator/voice/push, replace keys, change package identity or publish/replace an APK. Android emulator/physical-device offline sign-out, process termination, reconnect and account-switch acceptance must still be performed against a separately reviewed candidate; the existing signed release bytes do not acquire this fix from a source merge.
